# Bank Management System - Custom C++ Test Framework

## 1. Overview

The Sprint 2 automated testing system uses a lightweight, custom-built C++ test framework.

It provides test registration, assertion checking, exception handling, execution summaries, and process exit status without requiring an external testing library.

## 2. Framework Components

### 2.1 TestCase Structure

The TestCase structure stores:
- The name of a test case.
- A function pointer referring to the test function.

### 2.2 Test Registry

The testRegistry() function maintains a static vector containing registered test cases.

The registry provides a central collection that the test runner can iterate through.

### 2.3 Automatic Test Registration

The TestRegistrar structure registers test functions when their corresponding static registrar objects are initialized.

This allows test files to register tests without manually adding every test to the test runner.

### 2.4 TEST Macro

The TEST(name) macro:
- Declares a test function.
- Creates a static TestRegistrar object.
- Registers the function using its name.
- Defines the test function body.

### 2.5 CHECK Macro

The CHECK(condition) macro evaluates an assertion.

If the condition is false, it throws a runtime_error containing:
- The failed condition.
- The source-code line number.

This allows the test runner to report the failure.

## 3. Test Execution

The test_main.cpp file acts as the test runner.

Its execution sequence is:

1. Initialize passed and failed counters.
2. Display the automated test heading.
3. Iterate through the registered test cases.
4. Execute each test function.
5. Increment the passed counter if execution succeeds.
6. Catch standard exceptions and report assertion failures.
7. Catch unexpected exceptions and report them.
8. Display the final test summary.
9. Return an appropriate process exit code.

## 4. Exception Handling

Each test is executed independently inside a try-catch block.

A failed assertion does not immediately terminate the entire test suite.

The runner catches:
- std::exception, including runtime_error generated by CHECK.
- Other unexpected exceptions.

This allows subsequent registered tests to execute.

## 5. Test Results

The runner displays:
- PASS for successful test cases.
- FAIL for unsuccessful test cases.
- Passed count.
- Failed count.
- Total executed test count.

The process returns:
- 0 when all tests pass.
- 1 when one or more tests fail.

This exit status allows automated CI workflows to detect test failures.

## 6. Integration with GitHub Actions

The test executable is compiled and executed as part of the GitHub Actions workflow.

A non-zero exit status causes the test step, and consequently the workflow job, to fail.

## 7. Advantages

- No external testing framework dependency.
- Automatic test registration.
- Centralized test execution.
- Clear assertion failure messages.
- Independent execution of test cases.
- CI-compatible exit status.
- Simple integration with the existing C++ project.
